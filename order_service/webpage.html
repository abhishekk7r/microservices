Architectural Vision & Goals

This document provides a comprehensive explanation of the microservices architecture for our e-commerce platform. The primary goal is to build a scalable, resilient, and maintainable backend by decomposing a traditional monolithic application into a suite of independently deployable microservices. This approach allows for greater flexibility, technology diversity, and fault isolation.

Communication Patterns

This system uses two primary communication styles. Click the buttons below to highlight the corresponding data flow on the diagram above.

Synchronous Communication (REST Call)

Used for immediate, blocking requests where a response is required to proceed. It's simple and direct, perfect for real-time queries.

Example:

The Order Service must wait for a response from the Inventory Service to confirm stock availability before finalizing an order.

Asynchronous Communication (Event-Driven)

Used for non-blocking tasks that can be processed in the background. This improves system responsiveness and decouples services.

Example:

The Order Service sends an "OrderPlaced" event to Kafka and immediately confirms the order to the user. The Notification Service later consumes this event to send an email, without making the user wait.

Key Architectural Principles

Single Responsibility Principle

Each microservice has a narrow, well-defined purpose and owns a specific business domain. The Inventory Service only cares about stock; the Product Service only cares about product data. This makes services easier to understand, develop, test, and maintain independently.

Database Per Service

This is a cornerstone of microservices. Each service owns and controls its own database. Other services can only access this data through the service's public API. This prevents tight coupling between services and allows each service to choose the database technology best suited to its needs (e.g., MongoDB for products, MySQL for orders).
